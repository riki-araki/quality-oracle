# 実PRでの検証手順（①意図ドリフト / ②訂正の資産化 / ③情報量で並べる）

核（オラクル引き出し）と価値ループ（decisions/0022–0024）を、**実際のPR/コード**で通しで確認するための最小手順。
ローカル Web UI（`npm run dev`）で行う。データは外に出ない（§5.1）。

## 0. 前提
- `.env` に `ANTHROPIC_API_KEY`（LLM 呼び出し用）。private リポジトリを観測するなら `gh auth login` 済み（`GITHUB_TOKEN` 自動利用・decisions/0013）。
- `AUTH_SECRET` 設定済み（マルチユーザー・decisions/0018）。未登録なら最初の登録者が admin。
- 起動: `npm run dev` → ブラウザで開く。ログイン（未登録ならサインアップ）。

## 1. 対象を用意する（プロジェクト → 課題）
1. サイドバー「＋」→ **プロジェクト作成**。GitHub リポジトリ（`owner/repo`）を連携。
2. **課題を立てる**（`/issue/new`）: ソースに**実PRを指定**（連携済みなら PR番号だけでOK）。
   - PR全体: `#123` / 単一ファイル: `path/to/file.ts[@ref]`。
3. （任意）課題の**概要**を書き、「AIで下書き」で**AI分析ナレッジ**を作る（観測の前提知識になる）。

## 2. ③ 情報量で並べる（最初の観測で即確認）
1. 「項目を追加」→ **オラクル質問を生成**（主体×強度を選択・デグレ観点ON）。十数秒。
2. 候補一覧が **「当たりそうな順」** に並ぶことを確認（低確信・矛盾/抜け・高リスクが上、種別チップ付き）。
   - 末尾の折りたたみ **「低情報（鏡に近い）」** に、AIが高確信の単なる挙動が畳まれていること。
   - ✅ 見るべき質問が上に来て、鏡に近い質問が下がっていれば③はOK。

## 3. 核＋② の素地（承認して意図を貯める）
1. 各候補を **✓意図どおり→採用 / ✗違う→修正して採用 / 捨てる** で捌く。
   - **意図と違う挙動を見つけたら ✗（訂正文を入れる）**。これが「テスト前に見つけたバグ」＝ツールの価値の芯。
2. `/project` で **✗訂正率（テスト前検出）** と **レンズ別の当たり率**（どの主体×強度が実際に ✗/? を生んだか）を確認。
   - ✅ ✗訂正が出て、当たり率が数字で見えれば核＋③（較正）はOK。

## 4. ② 訂正の資産化（訂正が数件たまったら）
1. `/project` の **「学習ナレッジ（訂正から）」** →「訂正から教訓を抽出」。
2. ✗訂正から一般化された教訓が出ることを確認（必要なら手編集で整える）。
3. **別の課題**（同プロジェクト）を観測すると、この教訓が `<前提知識>` に注入され質問が変わることを確認。
   - ✅ 過去の訂正が次の観測の質問に効いていれば②はOK。

## 5. ① 意図ドリフト検出（コードが変わったとき）
承認済みの意図（採用＋declaredIntent）が**現在のコードと矛盾**していないかを検査する。差分が要るので:
- **PRが更新された場合**: 同じ課題の「意図ドリフト」パネル →「ドリフトを検査」。更新後のコードを再観測し、承認済み意図と矛盾する新挙動だけが出る。
- **手早く再現する場合**: 課題のソースを、意図を承認したときと**挙動が変わったファイル/ref**に向けて検査する（例: `path@old` で承認 → `path@new` で検査）。
1. 検出が出たら各件を **「新挙動を正とする（意図を更新→回帰テスト再生成）」/「無視」** で捌く。
   - ✅ 承認済み意図と食い違う変更が「ドリフト」として上がれば①はOK。

## 6. 使用状況の確認（任意・admin）
- `/ai` で、上記の観測/尋問/テスト生成/ナレッジ/ドリフト/訂正資産化の**回数・トークン・概算コスト**を確認。

---
## 見るべき勘所（合否の目安）
- **核**: 鏡化していない（コードの言い換えでない）質問が出て、人が ✗ で実バグ/仕様の穴を拾える。
- **①**: 承認した意図に反する変更を検出できる（意図レベルの回帰ネット）。
- **②**: 過去の訂正が次の観測の質問を賢くする（使うほど効く）。
- **③**: 当たりそうな質問が上に来て、鏡に近い低情報が下がる（✓スルー抑止）。レンズ別の当たり率で効く観点が見える。

うまくいかない点（鏡化が多い/質問が的外れ/ドリフト誤検出 等）が出たら、それ自体が次の改善対象。プロンプト雛形（`docs/prompts/`）が単一の真実源なので、そこを調整する。
