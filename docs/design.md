# 設計ドキュメント — quality-oracle（仮称）

最終更新: 2026-06-28

このドキュメントは、構想から最上流エンジン設計までの議論をまとめたもの。
各判断には「なぜそうしたか」を併記している（後から覆すときに前提を確認できるように）。

---

## 1. 解く問題

### 1.1 背景
AIによる実装が一般化し、システムの知見がない人が開発に参入する。
その結果、開発のボトルネックは「コードを書くこと」から
**「書かれたものが正しいかを判断すること」**へ移った。

### 1.2 核心＝オラクル問題
テストで本当に難しいのは、テストを書く・実行することではなく、
**「正しい振る舞い（期待値）とは何か」を定義すること**。これを oracle problem と呼ぶ。

知見のない人でも、ツール操作やコード生成はAIが肩代わりできるが、
「この入力に対してこの出力が正しい」という判断だけは、
本質的にドメインの当事者（人間）にしかできない。

### 1.3 AI時代の循環参照（最大の罠）
AIがコードもテストも生成すると、次が起きる:

```
AIがコードを誤解 → 同じ誤解のままテストも生成 → テストは通る → でも仕様は満たしていない
```

採点者と解答者が同一人物（同一AI）だと、間違いが検出できない。
この問題は業界でも2026年時点で正面から認識されている（§4参照）。

---

## 2. 誰に向けるか

### 2.1 ターゲット
**技術はある側の開発者で、テスト・品質が弱い組織に属している人。**
具体的には、品質を軽視する組織の中で「軽視されている現状に困っている少数」
（CTO・テックリード・過去に障害で痛い目を見た人）。開発者本人がまさにこの層。

### 2.2 これは技術問題ではなく組織・文化の問題
品質を軽視する組織は「ツールがないから」軽視しているのではない。
無料／安価なツールは既にあるのに、やらない。原因は:

- 「動いてるからいい／リリース優先」という**優先順位**の問題
- テスト設計に**時間が割かれていない**という配分の問題
- そもそも**何をテストすべきか分からない**という知見の問題

技術で解けるのは3つ目だけ。1・2は「やる気のない人はツールを開かない」壁に当たる。
よって狙う的は「機能」ではなく**「行動を変えること」**と定義し直す。

### 2.3 売る相手を分ける
- 軽視しているのは現場やリリース優先の空気＝**使う人**。
- 困っているのは少数の責任者＝**買う人**。
- この2者を分け、「チームに品質を強制する道具」として責任者が導入する形を狙う。

## 3. 戦略上の位置づけ

### 3.1 何が差別化で、何がそうでないか
| 要素 | 状態 | 扱い |
|---|---|---|
| 記録＋アサーション付け | 完全にコモディティ | 差別化にならない |
| 自然言語→テスト生成 | 急速に成熟 | 差別化にならない |
| 自己修復（self-healing） | AIツールの標準 | 差別化にならない |
| Slack通知連携 | 既に全社が保有 | **差別化にならない（table stakes）** |
| Backlog連携 | 主要ツールで手薄 | **入口（beachhead）にはなるが堀ではない** |
| オラクルの引き出し | ほぼ未開拓 | **これが核（moat候補）** |

### 3.2 差別化と堀は別物
連携機能は簡単に真似される。Backlog連携で人が集まった瞬間に大手が同等機能を出して終わり。
したがって**連携は「顧客を呼び込む入口」、核は「オラクル引き出し」**と役割を分ける。

### 3.3 セグメントの一致
「AIにコードを書かせる非エンジニアが増える」現象が最も濃いのは、
**Backlogが強い受託／SIer・社内開発の世界**。
ターゲット（困っている技術者）と入口（Backlog圏）がきれいに一致する可能性がある。

## 4. 競合の現状（2026年時点の調査メモ）

> 出典記事はいずれも2026年前半。詳細URLは調査時の検索結果に基づく要約。

### 4.1 海外
- **mabl**: record＋GenAIアサーション＋自然言語テスト生成。2026年4月に
  「Active Coverage」発表（AIコーディングの速度に品質検証を追従させる狙い）。エンタープライズ価格。
- **Testim / Playwright codegen**: 記録＋アサーションは標準。Playwright codegenは無料だがCLI・コード前提。
- **Aviator Verify**: 「テスト≠検証」を掲げ、AIコードを**人間承認済みの仕様／受け入れ基準**と照合。

- **Meticulous / Autonoma 等**: 本番セッション記録の再生や intent-based 回帰。

→ オラクル系は動き始めているが、いずれも**「書かれた仕様との照合」止まり**。
   **「仕様を書けない人から問いで意図を引き出す（elicitation）」は誰も核に置いていない。**

### 4.2 国内
- **Autify**（国内最有名、2019ローンチ、自然言語エージェント Autify Nexus あり）
- **MagicPod**（国産、日本語に強い、月39,800円〜、実行回数無制限、モバイル強い）
- ほか T-DASH / ATgo / SKYATT、mablも日本語化済み。

→ **ノーコードE2Eというカテゴリは日本でも既に埋まっている。**
   ただし大企業ですらテスト自動化率は約33%（Tricentis 2024）。
   **「道具はあるのに現場に浸透していない」**のが実態。
   競合不在ではなく「競合はいるが皆が使いこなせていない」が本質。

## 5. アーキテクチャ上の決定

### 5.1 ローカル優先・ホスト対応可能（local-first, hosted-capable）
低価格を狙うとき、クラウドでのテスト実行は地雷。
ブラウザ実行は提供側に実コストがかかり、使われるほど赤字になる。
→ **実行はユーザーのローカルマシンで回す**。これは同時に
「自分用／社内のみ／データを外に出さない」という前提とも噛み合い、
限界費用ゼロ・プライバシー安全・個人開発で維持可能、を得られる。

> **更新（2026-06-28, → [decisions/0002](../decisions/0002-saas-capable-premise-and-nextjs.md)）**
> 将来のホスト型SaaS提供を選択肢として前提に追加した。
> **ローカルを既定**として上記の強み（プライバシー・限界費用ゼロ）は維持しつつ、
> マルチユーザー/ホストへ作り直しなしで到達できる設計にする（スタックは Next.js、
> engine をフレームワーク非依存に分離）。
> ただし「使われるほど赤字」の罠は依然有効なので、**重い実行（LLM呼び出し・将来のテスト実行）は
> ホストの致命的コスト経路に載せない**（顧客キー／ローカルランナーで負担し、SaaS側はUI・台帳・管理に寄せる）。

### 5.2 E2E（受け入れ）優先、単体・結合は北極星
「単体・結合・総合」を最初から全部やると沈む。
観測可能な振る舞いを扱うE2E／受け入れテストが非エンジニアと最も相性が良いので、
**最初はE2E一本**。単体・結合は将来像として保持。

### 5.3 スコープ規律（最重要）
最大のリスクは技術でも競合でもなく、
**事業計画を作り込みすぎて肝心の道具が完成しないこと**。
管理・可視化・連携・複数動線は**すべて後回し**。
最初の楔は必ず「価値を生成する側」に置く（管理・可視化・連携はその出力）。

### 5.4 最初の楔＝一本の動線を1分で診断するループ
1. AIが重要動線（例: ログイン→決済）をクロールして**地図化**（診断的可視化の最小版）
2. その動線に対して**試験項目をAIが提案**（オラクルの核）
3. 実際に回して**「ここが壊れている／無防備」を1分で見せる**（買い手を動かす一撃）

「現状がいかにヤバいか」を突きつける診断レポートは、中身がなくても価値になる
（むしろ中身＝テストが無いことそのものが価値の証明になる）。

## 6. 最上流エンジン — テスト項目生成（オラクル引き出し）

### 6.1 役割の反転
現状の工程: 「AIが採点基準を作る／人間が採点する」。
これを反転し、**「AIは観測と問いだけ／人間は正解の宣言だけ」**にする。
これだけで循環参照（§1.3）が切れる。

### 6.2 全体の流れ
```
① AIが書いたコード
      ↓
② AI＝観測者   … 実際に何をしているかだけを抽出（解釈・評価は禁止）
      ↓  ＋ 確認質問リストを生成（カテゴリ別・リスク順）
③ 人間＝承認者 … 各項目を ✓意図通り / ✗違う→正す / —不要 / ?わからない
      ↓                       └─ ✗と? = テスト実行前に見つかる不具合・仕様の穴
④ 承認済みの意図 ＝ 組織で初めて文章化された「正解の記録」（仕様）
      ↓
⑤ テスト項目を生成 … ✓→回帰テスト / ✗→今すぐ落ちるテスト（=既知バグ）
      ↓
（コード変更時）→ ②へ戻り、差分が出た所だけ再確認
```

### 6.3 鏡化を防ぐ唯一にして最強のフィルタ
各質問に自問させる:
> 「この質問は、コードを読み直せば答えられるか？」
> 答えられるなら、それは質問ではなく観測。捨てる。

良い質問の定義 = **コードを読んでも答えられず、意図を知る人間にしか答えられないこと。**

### 6.4 二段パイプライン
観測と尋問を別のAI呼び出しに分離する（一発でやると鏡化する）。

- **Pass 1（観測）**: 何をするかだけを事実として構造化抽出。評価・意図推測は禁止。
- **Pass 2（尋問）**: Pass 1の構造化インベントリを入力に、質問だけを生成。

効能: 観測が監査可能になる／Pass 2が生コードでなく整理済みインベントリを相手にするので
鏡化しにくい／観測と判断のどちらが外れたか切り分けられる。

実際のプロンプト雛形は [`prompts/pass1-observation.md`](prompts/pass1-observation.md) と
[`prompts/pass2-interrogation.md`](prompts/pass2-interrogation.md)。

### 6.5 「やっていないこと」を漏れなく出させる
バグの大半は「コードが間違ったことをする」ではなく「必要なことをしていない」に潜む。
だが「何が欠けてる？」とオープンに聞いてもAIは網羅できない。
→ **オープンな欠落探索を、クローズドな点検作業に変換する。**
「あるべき観点のチェックリスト」を渡し、各挙動×各観点を総当たりで点検させる。

観点リスト（エンジンの中核資産。育てていく）:
- 空・null・未入力
- 境界値（0／負数／最大／桁あふれ）
- 不正な型・形式
- 二重操作・同時実行（二重送信、競合）
- 依存先の失敗（API停止、DBエラー、タイムアウト）
- 認証・権限（誰が実行してよいか）
- 取り消せない操作（削除・送信・課金）のガード有無
- 状態の前提（ログイン済み・データ存在・順序）
- 部分的失敗・ロールバック
- 大量データ・上限

### 6.6 矛盾検出（外部仕様すら要らないオラクル）
知見ゼロの人がAIに書かせるとコードが自分自身と矛盾しやすい
（例: ある画面ではメール形式を検証、別画面では同項目を無検証で受理）。
矛盾は宝。**少なくとも一方が間違いだと、仕様を知らなくても確定できる**。
インベントリ全体を横断スキャンし、矛盾ペアごとに「どちらが正解？」を問う。
最も低コストでバグが採れる経路。

### 6.7 人間の負担を「承認だけ」に畳む
- **リスク順に並べる**: 金が動く／データが消える／認証・権限／取り消せない／主要動線 を最上段に。
- **1タップの4択**: ✓意図通り / ✗違う→正解:___ / —テスト不要 / ?わからない
- **「?わからない」は最重要シグナル**: 知見ある人すら不明＝組織の誰も正解を知らない箇所。
  AI実装者・依頼主・顧客に確認しに行くべき場所を可視化する。✓で流すと掛け違いが温存される。
- **AIの推測をデフォルト値に**: 全項目を白紙で問わず、最尤推定を初期選択にし、人間は例外だけ直す。

### 6.8 副産物 — テストを1行も実行する前にバグが出る
- コードがやっていること（AI観測） vs やるべきこと（人間が宣言＝オラクル） の**差分＝バグ**。
- 人間が「✗」「?」を押した瞬間、それは1回もテストを走らせる前に検出された欠陥。
- 「手動テスト→修正→再テスト」の何周分かが、上流の承認作業に前倒しされる。

### 6.9 記録される成果物（1項目=1レコード）
| 項目 | 中身 |
|---|---|
| 対象 | ファイル/関数/動線のどこか |
| 観測 | AIが見たコードの実際の挙動 |
| 宣言した意図 | 人間が承認・訂正した「正解」 |
| 状態 | 確認済 / 訂正(=バグ) / 不明(=要確認) / 対象外 |
| 優先度 | 金・データ・認証・不可逆・主要動線 |
| 生成テスト | この意図から作られたテスト項目 |
| 最終照合 | どのコードバージョンで確認したか |

この成果物が二役を果たす:
1. **生きた仕様書**（今の組織に存在しないもの）
2. **テストの生成元**
そして後で作る一元管理・可視化が「表示すべき中身」そのものになる（§5.3の順序がここで噛み合う）。

### 6.10 品質を測るデバッグ指標
1. 生成質問のうち「コードを読めば答えられる」割合 → 高ければ鏡化（理想ゼロ）
2. 観点リストの各項目に最低1問ぶら下がっているか → 空なら点検サボり
3. 人間が「✗違う」を押した割合（=テスト前バグ検出率）→ 価値の直接指標・最初の説得材料

### 6.11 二系統で「対応分の試験項目」を網羅する（種別 track・decisions/0016）
オラクル質問だけでは「未知のリスク/意図」しか拾えない。ソースから分かる**正常系（現状の挙動）**も
試験項目に要る。そこで項目に**種別(track)**を持たせ、由来の違う項目を一つの台帳に共存させる:

| track | 由来 | 性質 |
|---|---|---|
| `oracle` | オラクル質問（§6.2〜6.8） | 未知のリスク/意図。人が ✓/✗ で正解を宣言 |
| `normal` | 観測インベントリ → 回帰項目を生成 | **現状固定（回帰）**。correctness は主張しない |
| `manual` | 人が手入力 | 任意の補強 |
| `imported` | 実装者が JSON で一括取込 | 既存項目の移植 |

**重要な線引き**: §6.3 のアンチミラーは「**質問**」に効かせるもので「**テスト項目**」には効かせない。
`normal` は「コードを読めば分かる」が、それは捨てる対象（質問）ではなく**固める対象（回帰の土台）**。
正しさの判定は従来どおり**人が ✗（corrected）**で表明する。こうしてオラクルが穴を、正常系が土台を埋め、
§6.5「全挙動リスト → チェックリスト化」が両輪で完成する。`normal` は候補止まり（自動採用しない＝✓スルー対策）。

## 7. 対象組織の現行ワークフロー（出発点の実例）

```
AIでシステム知見のない人が実装
  → プロジェクトの形ができた段階でエンジニアが受け取る
  → AIにソースを読み込ませてテスト項目書を生成   ★ここに循環参照が埋まっている
  → エンジニア数名で分担して手動テスト
  → 結果を更新
  → クリティカルなものを修正
  → 再度手動テスト
  → リリース
```

危険地帯は「AIにソースを読ませてテスト項目書を生成」。
最初の実装者が知見ゼロのため、**正解（仕様）がどこにも文章化されていない**。
→ §6のエンジンを、この「テスト項目書生成」の工程に差し込むのが最初の一撃。
工程をほぼ変えず、生成方式だけを「実装の鏡」から「意図の承認」へ置き換える。
