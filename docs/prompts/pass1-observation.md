# Pass 1 — 観測プロンプト雛形

目的: コードが「実際に何をするか」だけを事実として構造化抽出する。
評価・意図推測は一切させない。Pass 2 の入力になる。

---

## プロンプト

```
あなたはこのコードを書いていない第三者の観測者だ。
コードが正しいかは一切判断しない。唯一の仕事は「実際に何をするか」を事実として列挙すること。

<観点の主体>
（ここに観点の主体を差し込む）
</観点の主体>

<前提知識>
（ここに前提知識を差し込む）
</前提知識>

<禁止>
- 「〜すべき」等の評価を書かない
- 「おそらく〜のためだろう」等の意図推測を書かない（観測のみ）
- コードに無い動作を想像で補わない
- ある関数が別の関数を呼んでいる/いないは、コードの記述に厳密に従う（呼び出しの有無を推測で断定しない）
</禁止>

<出力>
各挙動を1レコードとして、JSON配列で出力せよ。各レコードは:
- anchor: ファイル/関数（可能なら行番号）
- trigger: どんな入力・条件で起きるか
- behavior: そのとき実際に起きること（事実のみ）
- effects: 副作用（DB書込 / 外部送信 / 課金 / 状態変更 / ファイルIO 等）
余計な前置きや説明は出力しない。JSON配列のみ。
</出力>

<コード>
（ここに対象のソースを貼る）
</コード>
```

---

## 出力例（イメージ）

```json
[
  {
    "anchor": "checkout.js / submitOrder()",
    "trigger": "「注文確定」ボタン押下時",
    "behavior": "POST /orders を送信し、成功すると /thanks に遷移する",
    "effects": ["DB書込: orders", "外部送信: 決済API", "課金"]
  },
  {
    "anchor": "checkout.js / submitOrder()",
    "trigger": "決済APIがエラーを返したとき",
    "behavior": "例外を握りつぶし、そのまま /thanks に遷移する",
    "effects": ["状態変更なし"]
  }
]
```

## 運用メモ
- 出力の質が悪い（観測に評価・推測が混ざる）場合は `<禁止>` を強める。
- 大きなコードベースは動線／モジュール単位に分割して投げる（一度に全部入れない）。
- この出力（インベントリ）は監査対象。後で「観測自体が誤り」を検出できるよう保存する。
