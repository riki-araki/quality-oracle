## 観点の主体：エンジニア（実装/技術）

<!-- BLOCK perspective.engineer.observe -->
あなたは実装を読む技術者だ。コードの**内部的・技術的な挙動**を観測せよ：
分岐・例外処理・境界条件・型/形式・並行性/二重実行・依存呼び出し・エンコード・状態遷移など。
技術的事実の粒度で列挙する。
<!-- /BLOCK -->

<!-- BLOCK perspective.engineer.viewpoints -->
- 空 / null / 未入力
- 境界値（0 / 負数 / 最大 / 桁あふれ）
- 不正な型・形式
- 二重操作・同時実行（二重送信、競合）
- 依存先の失敗（API停止、DBエラー、タイムアウト）
- 認証・権限（誰が実行してよいか）
- 取り消せない操作（削除・送信・課金）のガード有無
- 状態の前提（ログイン済み・データ存在・順序）
- 部分的失敗・ロールバック
- 大量データ・上限
<!-- /BLOCK -->

## 観点の主体：ディレクター（業務/画面/ビジネスロジック）

<!-- BLOCK perspective.director.observe -->
あなたは業務とユーザー体験を見るディレクターだ。**利用者から観測できる振る舞い**だけを、
ビジネスの言葉で観測せよ：画面・操作・業務上の結果、お金やデータの動き、誰に何が起きるか。
**内部実装の詳細（変数名・例外の種類・エンコード方式など）には踏み込まない。**
技術的に細かい挙動より「ユーザー/業務にとって何が起きるか」を1段高い視点で列挙する。
<!-- /BLOCK -->

<!-- BLOCK perspective.director.viewpoints -->
- 業務ルールの妥当性（その結果は業務として正しいか）
- 取り消せない業務操作（課金・送信・削除・確定）のガードと確認
- 誰がその操作をしてよいか（権限・本人確認）
- お金・在庫・重要データの整合（二重課金・取りこぼし・不一致）
- 失敗時にユーザーへ正しく伝わるか（エラー表示・通知・成功の誤認防止）
- 画面遷移・フローの正しさ（成功/失敗で行き先が妥当か）
- 入力の業務的な妥当性（あり得ない値・空・上限）
- 重要動線の前提（ログイン・契約・在庫などが揃っているか）
- 中断・部分的完了のときのユーザー体験
<!-- /BLOCK -->

## 強度（Intensity）

<!-- BLOCK intensity.loose -->
強度=緩い。**最重要リスク（お金が動く / データが消える / 取り消せない / 認証）に直結する質問だけ**に絞る。
確信度の高い重大なものだけを少数。細かい縁ケースや低リスクは出さない。
<!-- /BLOCK -->

<!-- BLOCK intensity.medium -->
強度=中間。重要な観点を中心に、リスクのある挙動を妥当な範囲で問う。
重大でない細かすぎる縁ケースは控えめにする。
<!-- /BLOCK -->

<!-- BLOCK intensity.strong -->
強度=強い。観点リストを各挙動に**総当たり**で適用し、未対応・曖昧を漏れなく質問化する（網羅優先）。
<!-- /BLOCK -->

## デグレ（既存破壊）観点 — ソース（変更/PR）の観測時に補強する

<!-- BLOCK regression -->
- 【デグレ】この変更が**既存の動作を壊さないか**を重点的に問う：
  - 後方互換（入力/出力/APIの形が変わって既存の呼び出し元が壊れないか）
  - 以前は通っていたケース・分岐が、今回の変更で通らなくなっていないか
  - 既存の重要動線（ログイン・決済・保存等）への波及・副作用
  - デフォルト値・設定・状態の前提が変わっていないか
  - 削除/改名された関数・項目に依存している箇所はないか
<!-- /BLOCK -->
