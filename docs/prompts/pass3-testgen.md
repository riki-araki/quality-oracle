# Pass 3 — テスト生成プロンプト雛形

目的: 人間が承認した「正解の意図」(declaredIntent) から、観測可能な振る舞いのテスト項目を作る。
**コードは参照しない**（コードを採点基準にすると §1.3 の循環参照に戻るため）。
入力は §6.9 台帳の1レコード。出力は受け入れ/E2E 粒度・ツール非依存のテスト項目1件。

---

## プロンプト

```
あなたはテスト設計者だ。与えられた「承認済みの意図」を唯一の正解として、
その意図が満たされているかを確かめる受け入れテストを1件設計せよ。

<前提>
- 正解は declaredIntent（人間が承認・訂正した意図）。コードの現状は正解ではない。
- status=confirmed なら「意図通りの振る舞いが今後も保たれる」ことを確認する回帰テスト。
- status=corrected なら declaredIntent は現状コードが満たしていない正しい振る舞い。
  つまりこのテストは今は落ちる（＝既知バグを固定する）。
</前提>

<禁止>
- 実装の詳細（関数名・内部変数・特定ライブラリ）に依存しない。観測可能な振る舞いで書く。
- 単体・結合レベルに踏み込まない。利用者から見える受け入れ/E2E 粒度にとどめる。
- コードを推測で補わない。意図と観測の範囲で書く。
</禁止>

入力レコード:
<record>
（ここにレコードのJSONを貼る）
</record>

<出力>
次のキーだけを持つ JSON オブジェクトを1つ出力せよ（配列にしない・前置きしない）:
- title: テスト項目の見出し
- given: 前提（ログイン状態・データ・画面など）
- when: 操作・トリガ
- then: 期待される結果（= 承認された意図そのもの）
- rationale: なぜこのテストか（どのリスク・意図に対応するか）
</出力>
```

---

## 出力例（イメージ）

入力（status=corrected の例）:

```json
{
  "anchor": "checkout.js / submitOrder()",
  "observation": "決済APIがエラーを返しても例外を握りつぶし /thanks に遷移する",
  "question": "失敗時に成功画面を出すのは意図通りか？",
  "status": "corrected",
  "declaredIntent": "決済失敗時はエラーを表示し、成功画面に遷移しない"
}
```

出力:

```json
{
  "title": "決済失敗時は成功画面に遷移しない",
  "given": "カートに商品があり、決済APIが失敗を返す状態",
  "when": "「注文確定」を押す",
  "then": "エラーが表示され、/thanks（成功画面）には遷移しない",
  "rationale": "決済失敗をユーザーが成功と誤認するのを防ぐ（money リスク）。現状コードは握りつぶすため、このテストは今は落ちる＝既知バグ。"
}
```

## 運用メモ
- 生成は承認済み（confirmed / corrected）のレコードに限る。unknown/—/未決は正解が未確定なので作らない。
- `kind`（regression / known_bug）は status から機械的に決まるため、LLM には出力させない。
- テストの「実行」はしない（CLAUDE.md ガードレール）。ここは項目を出すまで。
