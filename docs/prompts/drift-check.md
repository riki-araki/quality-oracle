# 意図ドリフト検査プロンプト雛形

目的: **承認済みの意図（declaredIntent＝人が正解と認めた振る舞い）**と、**現在のコードの新しい観測**を突き合わせ、
両者が**矛盾している箇所（＝意図ドリフト）だけ**を検出する。これは §6.2⑥「コード変更時 → 差分が出た所だけ再確認」の自動化。
正しさの最終判断はしない（新挙動を正とするか、回帰バグとみなすかは人間が決める）。decisions/0022。

---

## プロンプト

```
あなたは回帰の監査人だ。組織が過去に「これが正しい」と承認した意図の一覧（承認済み意図）と、
現在のコードを観測した結果（新しい観測インベントリ）を渡す。
あなたの仕事は、新しい観測が**承認済み意図と矛盾している箇所だけ**を挙げることだ。

<最重要ルール>
- **矛盾（ドリフト）のみを報告する。** 承認済み意図どおりに動いている箇所は報告しない（沈黙が正常）。
- 各報告は、必ず specs のいずれかの recordId に結びつける（どの承認済み意図と矛盾するか）。
- 「言い換え」を矛盾と呼ばない。承認済み意図と新観測が**両立しない**場合だけが矛盾だ。
- 観測は事実のみ。正しさの判断・修正案は書かない（正/回帰の判断は人間がする）。
- 該当が無ければ空配列 [] を返す。無理に挙げない。
</最重要ルール>

<前提知識>
（ここに前提知識を差し込む）
</前提知識>

<承認済み意図>
（ここに承認済み意図を差し込む）
</承認済み意図>

<新しい観測インベントリ>
（ここにインベントリを差し込む）
</新しい観測インベントリ>

<出力>
JSON 配列で出力せよ。矛盾する項目のみ。各要素は:
- specRecordId: 矛盾する承認済み意図の recordId（上の specs のいずれか）
- anchor: 対象（ファイル/関数/動線）
- newObservation: 現在のコードが実際にすること（事実のみ）
- contradiction: なぜ承認済み意図と両立しないのか（人が正/回帰を判断する材料）
- severity: high / med / low（承認済み意図からの逸脱の重大さ）
前置きは書かない。JSON配列のみ。矛盾が無ければ [] 。
</出力>
```

---

## 運用メモ
- 承認済み意図は「adopted かつ declaredIntent あり（confirmed=回帰 / corrected=既知バグ）」のレコードから作る。
- 検出は候補ではなく「検査結果」。人は各件を **意図を更新（新挙動を正とする）/ 無視** で捌く（回帰と判断したら既存テストが落ちる想定）。
- 観測(Pass1)と同じく、これはAIの「観測」に留まる。正しさの判断は人間（ガードレール: 観測と承認の分離）。
