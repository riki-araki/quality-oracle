## 仕様として決めておくべき事項

コードを読んで「実装はされているが、仕様が明記されていないと判断・テストできない」箇所を整理します。

---

## 1. 入力バリデーション

### 1-1. 必須項目と形式

| フィールド | 現状 | 決めるべきこと |
|-----------|------|---------------|
| `name` | チェックなし | 必須か／最大文字数／使用可能文字 |
| `email` | チェックなし | 必須か／形式チェック（RFC準拠 or 簡易）|
| `department` | チェックなし | 必須か／選択式か自由入力か |
| `seminarId` | 存在確認のみ | 必須チェック自体がない |
| `card` | チェックなし | 必須か／形式は外部APIに委ねるか |

```js
// 現状：name が undefined でも通ってしまう
const { name, email, department, seminarId, card } = req.body;
```

## 2. 重複申込の扱い

```js
// 同一人物が同じセミナーに何度でも申し込める
const taken = entries.filter((e) => e.seminarId === seminarId).length;
```

**決めるべきこと**

- 同一メールアドレス＋同一セミナーの申込を禁止するか
- 禁止する場合のエラーメッセージとHTTPステータス
- 「同一人物」の判定キーは何か（メール／社員番号／その両方）

---

## 3. 締切日の境界値

```js
const today = new Date().toISOString().slice(0, 10);
if (today > seminar.deadline) { // 締切日当日はOK
```

**決めるべきこと**

- 締切日当日は申し込めるか（現状は可）
- 時刻を考慮するか（例：締切日の17:00まで）
- タイムゾーンはどこ基準か（現状はサーバーのUTC）

---

## 4. キャンセル可否の条件

```js
// 現在：いつでも・誰でもキャンセル可能
app.post("/api/entries/:id/cancel", async (req, res) => {
```

**決めるべきこと**

- キャンセル期限はあるか（例：開催3日前まで）
- キャンセルできるのは申込者本人のみか（認証の要否）
- セミナー開催後のキャンセルは可能か

---

## 5. 返金ルール

```js
// 現状：常に全額返金
await refundCharge(entry.chargeId);
```

**決めるべきこと**

- キャンセル時期によって返金額が変わるか（例：1週間前以降は50%）
- キャンセル手数料の有無
- 返金メールに返金額を記載するか（現状は金額なし）

---

## 6. 外部API失敗時の挙動

```js
// chargeCard が例外を投げたら → 500エラーが返るが entry は登録されない（OK）
const charge = await chargeCard({ amount: seminar.fee, card });
entries.push(entry); // ← 決済成功後に登録

// sendMail が失敗したら → entry は登録済みだがメールが届かない（問題）
await sendMail({ ... });
```

**決めるべきこと**

| 失敗箇所 | 決めるべき動作 |
|---------|--------------|
| `chargeCard` 失敗 | そのままエラー返却でよいか |
| `sendMail` 失敗（申込時） | 申込は確定扱いか／ロールバックするか／リトライするか |
| `refundCharge` 失敗 | エントリ削除を続けるか／停止するか |
| `sendMail` 失敗（キャンセル時） | キャンセル自体は確定扱いか |

---

## 7. セミナー一覧の表示条件

```js
// 締切済み・満席セミナーも一覧に出る
const list = seminars.map((s) => { ... });
```

**決めるべきこと**

- 締切済みセミナーを一覧に表示するか
- 満席セミナーを一覧に表示するか（`remaining: 0` で表示 or 非表示）
- 表示順のルール（現状は登録順）

---

## 8. 認証・認可

**決めるべきこと**

- 申込者の本人確認は不要か（現状は誰でも任意の名前で申し込める）
- キャンセルは申込者本人のみ可能にするか
- 管理者向けAPIは必要か（申込一覧閲覧など）

---

## 9. エントリIDの採番

```js
id: "e" + (entries.length + 1),
// キャンセルで splice するとIDが重複する可能性がある
// 例: e1登録→e2登録→e1削除→e3登録しようとすると…
// entries.length=1 なので "e2" が生成され重複
```

**決めるべきこと**

- IDの採番方式（連番 / UUID / その他）
- IDはキャンセル後も変えないか

---

## 優先度まとめ

```
【高】外部API失敗時の挙動（データ不整合に直結）
【高】エントリIDの重複問題（バグ確定）
【高】入力バリデーションの範囲
【中】重複申込の禁止ルール
【中】キャンセル条件・返金ルール
【低】一覧表示の絞り込み条件
【低】認証・認可（社内ツールの要件次第）
```
