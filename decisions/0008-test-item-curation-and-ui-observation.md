# 0008. テスト項目を一級化（候補→採用）し、UIから観測を起動できるようにする

- 日付: 2026-06-28
- ステータス: 採用

## 背景 / 何を決めるか
ゴールの再確認：**最終成果物は「テスト項目」**であり、AIの観測→質問は**テストを追加するときの出力（候補）**。
そのヒアリング結果（人間の承認＝オラクル）から**テスト項目を作り、管理画面で結果を残していく**のが目的。
現状は「質問＝項目」を全部一覧化しており、候補→採用の区別と、UIからの追加導線が無かった。これを (a) で埋める。

## 決定（(a) 採用ステップ）
1. **テスト項目を一級化**：record に `adopted`（採用フラグ）を追加。`adopted=false` は候補、`true` がテスト項目。
   - 採用は **confirmed / corrected（承認済み）に限る**（ヒアリングしてから採用、の順を強制）。
   - 採用時、テスト未生成なら **Pass3 を実行してテストを生成**し、項目を完成させる。
2. **UIから観測を起動できるようにする**（旧「観測は CLI 限定」を解禁）：
   - 課題の対象（codeRef）を**選んだ主体×強度**で再観測し、候補を追加する Server Action。
   - APIキー/トークンは Next が読む `.env`（空シェル変数の保険として `.env` 直読みフォールバックを実装）。
3. **観測→候補→採否は「項目作成」専用の別画面（`/add`）**にする。管理画面（課題詳細）には
   **採用したテスト項目だけ**を出す（候補は管理に混ぜない）。項目作成は「あくまで作成に使う機能」。
   - `/add` で各候補に **意図どおり→採用（現状を正解＝回帰）/ 違う→観点を修正して採用（＝既知バグ）/ 不採用→捨てる（破棄）** を選ぶ。
   - 採用＝承認（confirmed/corrected）＋テスト生成＋adopted を一手で実行。捨てる＝レコード削除。
   - 課題の項目は全観測（run）を横断して集約（採用がセッションを跨いで貯まる）。

## 理由
- 「候補→人が選ぶ→テスト項目」はユーザーの目的そのもの。adopted フラグで移行ゼロに実現できる。
- 採用済みのテスト項目は**承認済みの意図を仕様として抱える**ため、ただのテスト管理ツールと差がつく（核を保持）。
- UIから観測起動できないと「＋項目追加」が完結しない。`.env` フォールバックでキー解決の取りこぼしも防ぐ。

## 捨てた選択肢とその理由
- **全候補を自動でテスト項目化**: ノイズが増え、人の「選ぶ」意思が消える。採用は明示操作にする。
- **未承認でも採用可**: ヒアリング前のテスト化は意図不明のテストを生む。confirmed/corrected を必須に。
- **専用 test_item テーブル**: 移行コスト大。record の adopted フラグで足りる。

## 影響・前提（後で覆すとき確認すべきこと）
- UI観測はLLM呼び出しで十数秒かかる。ローカル/自ホスト前提なら可。サーバーレス化時はタイムアウトに注意。
- 次は **(b) 結果記録**：テスト項目ごとに pass/fail/未実施 を履歴で残す。これは**人手の結果記録であり、
  テストの自動実行ではない**ので CLAUDE.md「テスト実行機能は作らない」には抵触しない（§7 手動テスト工程）。
- 単体/結合（Level 軸）は引き続き保留（decisions/0007）。
