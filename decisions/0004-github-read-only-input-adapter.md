# 0004. GitHub を読み取り専用の入力アダプタとして解禁

- 日付: 2026-06-28
- ステータス: 採用（CLAUDE.md の「GitHub連携は明示指示まで作らない」を、入力に限り解禁）

## 背景 / 何を決めるか
PR を起点にオラクル引き出しを差し込みたい（§7「AIが書いたコードをエンジニアが受け取る＝PR」の瞬間）。
GitHub 連携は CLAUDE.md で明示指示まで保留としていたが、開発者が明示的に要望したため解禁する。
ただし design.md §3.1/§3.2 のとおり **連携は入口であって堀ではない**。核（オラクル引き出し）を太らせない。

## 決定
1. GitHub を **読み取り専用の入力アダプタ**として追加する（`src/engine/sources/github.ts`）。
   - `oracle run --pr owner/repo#123`: PR の変更ファイル**全文**を取得し、**連結して1 run**で観測。
   - `oracle run --gh owner/repo:path[@ref]`: 単一ファイルを観測。
2. 取得は **REST API + `GITHUB_TOKEN`（.env）**、追加npm依存なし（Node の fetch）。
   public はトークン不要、private はトークンで両対応。
3. engine の核は無改修。アダプタは sources/ に閉じ、CLI/UI 非依存＝将来ホストでも流用可。
4. `codeRef.path` に `gh:owner/repo#123@<sha>` を記録し、§6.9「最終照合」を効かせる。

（スコープ選択: 入力単位=変更ファイル全文 / 認証=REST+token / public・private両対応 / 連結して1run）

## 理由
- PR はターゲット工程（§7）の自然な差し込み点。入力源を増やすだけなら核を汚さず低リスク。
- REST+token は依存ゼロでホスト化にも耐える（`gh` CLI 依存より移植性が高い）。

## 捨てた選択肢とその理由
- **PR コメント/チェックへの書き戻し・Webhook/CI 連動**: 連携の作り込みで §5.3 リスク増。入口の次に回す。
- **`gh` CLI に委譲**: 楽だが gh 必須。配布・ホスト時に不利。REST を採用。
- **diff/patch だけ取り込む**: 文脈が欠落し観測が痩せる。全文連結を採用。

## 影響・前提（後で覆すとき確認すべきこと）
- **プライバシー**: private のコードも Anthropic API に送られる。ローカル既定の方針（§5.1）と、
  ホスト時のオプトライン（decisions/0002）を引き続き守る。トークンは .env のみ・ハードコード禁止。
- **書き戻しは未実装**: PR へのコメント/ステータス連携、Backlog 連携、証跡(画像/S3)管理、
  テスト項目の横断一覧/共有は**別途の判断**（commodity 層＝§3.1 table stakes。核の検証後に順序立てる）。
- レート制限: 大量ファイルの PR は contents API 呼び出しが増える。当面は許容、必要なら blobs/tree API へ。
