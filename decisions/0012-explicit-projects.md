# 0012. プロジェクトを一級エンティティ化し、レコードを課題へ明示リンク

- 日付: 2026-06-28
- ステータス: 採用

## 背景 / 何を決めるか
これまでプロジェクトは codeRef（リポジトリ名）から導出されるだけで、自由に作れなかった。
「プロジェクトも追加したい」（複数リポ/PRをまたいで束ねる単位）に応える。
そのためには課題の所属を「導出」でなく「明示」にする必要がある（プロジェクトをリポジトリから切り離すため）。

## 決定
1. **明示プロジェクト `project_meta`**（key, label, description, created_at）。サイドバーの「＋」から作成（`/project/new`）。
   課題ゼロでも表示される。
2. **レコードを課題へ明示リンク**：runs/records に `issue_id` 列を追加。
   - 既存行は codeRef からの導出値で **バックフィル**（非破壊・冪等。検証: 90件すべて一致・件数不変）。
   - 観測実行（UI/CLI）時、その課題の id を runs/records にスタンプする。
3. **課題作成でプロジェクトを選ぶ**（`/issue/new` のドロップダウン）。課題の projectKey は選択値。
   これにより、PRソースの課題でも任意のプロジェクトに束ねられる（リポジトリと非結合）。
4. ツリー構築（buildTree）は records を `issue_id` でグルーピングし、明示プロジェクト ∪ 導出プロジェクトを表示。

## 理由
- プロジェクト＝ユーザー定義の束（製品・案件）。リポジトリと固定で結びつける必然性はない。
- 明示リンク（issue_id）にすれば、プロジェクトを自由に定義しても records が正しく課題に紐づく。
- バックフィルで既存データを壊さず移行できる（id は導出値と一致するため、移行後も grouping 不変）。

## 捨てた選択肢とその理由
- **プロジェクト＝リポジトリのまま（空プロジェクトだけ作成可）**: 複数リポをまたぐ束ねができず要望に応えられない。
- **0010 時点で issue_id を入れる**: 当時は不要でリスク回避を優先。要望が出た今、バックフィル付きで安全に導入。

## 影響・前提（後で覆すとき確認すべきこと）
- 既存の導出課題は projectKey=リポジトリ名のまま。明示プロジェクトに移したい場合は将来「課題の移動」機能が要る。
- プロジェクト key は `p_<hash(label)>`。同名プロジェクトは同一視（更新）される。
- 課題のソースとプロジェクトは独立。観測対象（source）は課題が持ち、束ね（project）は別軸。
