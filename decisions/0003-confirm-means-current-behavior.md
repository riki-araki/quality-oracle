# 0003. ✓（意図通り）の意味を §6.2 に揃える

- 日付: 2026-06-28
- ステータス: 採用

## 背景 / 何を決めるか
⑤ テスト生成（§6.2⑤）を実装したところ、`regression / known_bug` のラベルが信用できないと判明した。
原因は ✓（confirmed）の意味のズレ:
- §6.2 の前提: ✓ ＝「**今のコードの挙動が正しい**」→ テストは今通る＝回帰。
- 旧実装: `confirmed` の declaredIntent に Pass2 の `assumption`（AIが推測する“正しい姿”＝多くは修正案）を採用していた。
  そのため ✓ なのに declaredIntent が「修正後の姿」になり、現コードは満たさず、生成テストは実際には今落ちる＝既知バグ。
  生成テスト自身が「✓なのに既知バグ」と表現し、矛盾が露見した。

## 決定
✓ / ✗ の意味を design.md §6.2 に揃える:
1. `confirmed`（✓意図通り）→ declaredIntent ＝ **観測（現状の挙動）**。テスト種別 = regression（今通る）。
2. `corrected`（✗違う）→ declaredIntent ＝ 人間の訂正文。テスト種別 = known_bug（今落ちる）。
3. Pass2 の `assumption`（AI推測の正解）は **✗訂正欄のデフォルト値**としてのみ使う（§6.7「AI推測をデフォルト」はここで生かす）。
   ✓ では使わない。

## 理由
- これで `kind`（regression / known_bug）が status から機械的に正しく決まる（意図 vs 現状の関係が status に一致するため）。
- コードではなく承認済みの意図からテストを起こす方針（§1.3 回避）は維持。
- 変更は `setDecision`（confirmed 分岐）と承認UI/CLIのラベルのみで最小。

## 捨てた選択肢とその理由
- **kind を「意図 vs 観測の一致」で都度判定**: 判定に追加のLLM一手か人間の一押しが要りコスト増。status で一意に決まる本案がよりクリーン。
- **据え置き**: 誤ラベルのまま「テストの生成元」を汚すため不可。§6.7「✓で流すと掛け違いが温存される」を地で行ってしまう。

## 影響・前提（後で覆すとき確認すべきこと）
- ✓ は「現状を正解として固定する」宣言になった。バグを ✓ で流すと、その**バグ挙動を回帰テストで固定**してしまう。
  これは §6.7 の警告どおりで、UI/運用で「✓ は現状肯定」と明示する必要がある（ラベル反映済み）。
- 既存の承認済みレコードは旧ルールの declaredIntent を持つため、本変更後に再適用して作り直す必要がある。
