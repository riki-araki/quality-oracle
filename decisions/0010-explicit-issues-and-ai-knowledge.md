# 0010. 課題を一級エンティティ化し、AI分析ナレッジを観測に注入する

- 日付: 2026-06-28
- ステータス: 採用

## 背景 / 何を決めるか
これまで課題は codeRef から「導出」されるだけだった。タイトル/概要/AI分析ナレッジ/試験項目一覧を持つ
「プロジェクトから課題を立てる」体験には、課題を**一級エンティティ**にする必要がある。
あわせて「与えられたソースや概要からテスト観点作成に効くナレッジを貯める」を実装する。

## 決定
1. **明示課題 `issue_meta`**：id, project_key, title, overview, source_kind, source_ref, knowledge, created_at。
   - **id は導出課題と同一**（`issueId(projectKey, issueKey)`）。＝既存の導出課題と明示課題を統合し、移行ゼロ。
   - source（PR / ファイル / ローカル / なし）が観測対象。project_key は source から導出。
2. **プロジェクトから課題作成**（`/issue/new`）：タイトル・概要・ソースを入力して作成。
   管理画面（課題）に 概要 / AI分析ナレッジ / 試験項目一覧 を表示・編集。
3. **AI分析ナレッジ**：概要＋ソース（PR文・コード）から、テスト観点作成に効く前提知識を **AIが下書き**
   （`docs/prompts/knowledge-analysis.md`・単一の真実源）。人が編集して育てる。
   - このナレッジを **観測/尋問プロンプトの `<前提知識>` に注入**する。コードだけでは出ない業務前提・要件・
     用語を踏まえた質問になり、director レンズ（0007）と相乗効果＝核を深める。
4. ツリー構築は「明示課題 ∪ 導出課題」を同一 id で統合（`buildTree(issues, records)`）。

## 理由
- 「課題＝レビュー単位」に概要・ナレッジを持たせることで、観点の質が上がり、複数人の共有も安定する。
- 同一 id 統合により既存データ（records/結果/証跡/採用）を一切壊さずに移行できる。
- ナレッジ注入は、コードに無いドメイン知識をオラクル引き出しに供給する正攻法（§6 の核に沿う）。

## 捨てた選択肢とその理由
- **runs/records に issue_id 列を足して厳密に正規化**: 移行コストとリスク大。導出 id 統合で十分。
- **ナレッジをテスト項目に持たせる**: ナレッジは課題（レビュー単位）の資産。課題に持たせる。
- **ソースなし（純手動）課題でコード無し観測**: パイプラインがコード前提。今回は source あり前提、none は箱だけ。

## 影響・前提（後で覆すとき確認すべきこと）
- source が PR の場合、観測は最新 head を取得（id は PR 番号で安定）。private は GITHUB_TOKEN 必須。
- 「なし」ソースの課題は観測できない（コード無し）。概要だけからの観点生成は将来の別対応。
- ナレッジは LLM の下書き＋人手編集。鵜呑みにせず「不明は不明」を守る運用（雛形に明記）。
