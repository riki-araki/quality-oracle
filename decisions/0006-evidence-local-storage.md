# 0006. テスト項目をテーブル＋詳細画面にし、証跡をローカル保存で導入

- 日付: 2026-06-28
- ステータス: 採用

## 背景 / 何を決めるか
手動テストの集約・共有のため、各テスト項目に「証跡（スクリーンショット等）」を残したいという要望。
証跡管理は design.md §3.1 ではコモディティ層で、§8 では「後回し（核の検証後・ホスト化と同時に）」として
S3 等が候補に挙がっていた。今回これをスコープに入れる判断をする。

## 決定
1. 課題詳細の項目表示を**テーブル化**し、行クリックで**項目詳細画面**（`/item/[id]`）へ進めるようにする。
   - 承認（4択）は一覧から詳細へ移す＝「開かないと判断できない」ことで ✓スルー（§6.7）も抑止する。
2. 詳細画面で**証跡（画像）を格納**できるようにする。**まずローカル保存**:
   - ファイル実体は `data/evidence/<recordId>/`（`.gitignore` 済み）。メタは台帳DB（`evidence` 表）。
   - 配信は `/api/evidence/[id]`。アップロード/削除は Server Action。PNG/JPEG/GIF/WebP・8MBまで。
3. **S3 等クラウド保存はまだやらない**。ホスト化（decisions/0002）と同時に、保存先を抽象の背後で差し替える。

## 理由
- 「複数エンジニアが同一フォーマットで品質をぶらさず管理」（§6.9 台帳の出力）に、証跡が加わると手動テストの
  集約・共有が回り始める。テーブル＋詳細は管理しやすさの定石。
- §5.1「クラウドは使うほど赤字」の罠を避けるため、まずローカルで形を固める。S3 直行はしない。
- 承認を詳細に置くことで、見た目を整えるほど速くなる「雑な全✓」を構造的に抑止できる。

## 捨てた選択肢とその理由
- **いきなり S3 連携**: §5.1 のコスト罠・インフラ重い・ホスト前提。ローカル先行が正しい順序（§8）。
- **画像を SQLite BLOB に格納**: 肥大・取り回し悪い。ファイルはディスク、メタのみDBにする。
- **一覧にも承認ボタンを残す**: ✓スルーを助長する。判断は詳細画面に集約。

## 影響・前提（後で覆すとき確認すべきこと）
- 証跡（コード/画像）はローカルに置く＝ローカル既定の方針（§5.1）と整合。ホスト時は外部送信になるため
  オプトイン＋保存先抽象化（S3/署名URL）を別途設計する。
- Next の file 操作により build で NFT 警告が出る（ローカルでは無害）。ホスト化時にトレース設定で対処。
- 証跡は record（=質問/テスト項目）単位。課題単位や手動テストケース単位の証跡が要るなら将来拡張。
