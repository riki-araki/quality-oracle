# 0022. 意図ドリフト検出（承認済みの意図 vs 現在のコードの再観測）

- 日付: 2026-07-01
- ステータス: 採用

## 背景 / 何を決めるか
- design.md §6.2 の全体ループは「（コード変更時）→ ②へ戻り、差分が出た所だけ再確認」で閉じる。だが現状は
  承認済みの意図（declaredIntent）が**一度記録されて終わり**で、コードが変わっても放置される。「生きた仕様」が
  スローガンに留まっていた。
- そこで **①意図ドリフト検出**を実装する（3案の1番手）。承認済みの意図と、現在のコードの新しい観測を突き合わせ、
  **矛盾（ドリフト）だけ**を検出して、人が「新挙動を正とする / 回帰バグ」を判断できるようにする。

## 決定
1. **AIは観測して矛盾を挙げるだけ・正しさは人が決める**（ガードレール順守）。ドリフト検査＝Pass1観測 ＋ 追加の
   「突き合わせ」1呼び出し。新挙動を正とするか回帰バグとみなすかは**人間**が決める（§6.7 の役割分担を維持）。
2. **鏡化にはならない**（§6.3）。判定材料は「コード」ではなく「**過去に人が承認した意図** vs 新観測」。
   コードを読むだけでは答えられない＝アンチミラーを自然に満たす。
3. **検査対象＝生きた仕様**：`adopted` かつ `declaredIntent` あり（confirmed=回帰 / corrected=既知バグ）のレコードを
   承認済み意図として渡す。1件も無ければ検査しない（`specCount=0`）。
4. **プロンプトは単一真実源**：`docs/prompts/drift-check.md`。「矛盾のみ報告・言い換えは矛盾でない・該当なしは []・
   各報告は specRecordId に結びつける」を明記。出力は Zod（`DriftOutput`）で実行時検証し、実在する specRecordId に
   結びつく報告だけ採用する（幻の ID を弾く）。
5. **検査結果は台帳に保存**：`drift_findings` テーブル（issue_id/spec_record_id/anchor/approved_intent/new_observation/
   contradiction/severity/code_hash/status）。再検査時は `open` を掃いて置き換え、`dismissed/resolved` は残す（冪等・非破壊）。
6. **対応は2択**：
   - **意図を更新（新挙動を正とする）** → 該当レコードの declaredIntent を新観測で上書きし confirmed に戻す。既存テストは
     無効化して**回帰テストを再生成**（`updateIntent` → `generateTest`）。検出は `resolved`。
   - **無視** → 検出を `dismissed`。回帰バグと判断した場合は放置＝その意図のテストが落ちるべき、という運用。
7. **再観測レンズは engineer/strong 固定**（回帰の監査なので技術主体・総当たり）。UI は課題画面の「意図ドリフト」パネル
   （承認済み意図が1件以上 かつ ソースが UI 再観測可能なときにボタン表示）。
8. **AI使用量に計上**：突き合わせ呼び出しは `AiUsageKind="drift"` として ledger.ai_usage に記録（decisions/0021 に整合）。

## スコープ規律との整合
- §6.2 のループを閉じるだけで、新しい外部連携・自動テスト実行ではない（ガードレール非抵触）。
- 追加は最小（1テーブル＋1パネル＋1プロンプト＋2アクション）。差分の自動修正やPR書き戻しはしない。

## 捨てた選択肢
- **検出を候補（records）として track を増やす**：一覧/集計/✗訂正率に混ざり複雑化。→ 別テーブルの「検査結果」に分離。
- **AIに「正/回帰」まで判定させる**：核（人が正しさを決める）を侵す。→ AIは矛盾提示まで。
- **コード差分（diff）ベースで検出**：実装差分に振り回される。→ 「承認済みの意図 vs 現状の観測」の意味レベルで見る。
