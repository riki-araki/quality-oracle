# 0018. 本格マルチユーザー化（認証・ユーザー管理・データ分離）— §8 の解禁

- 日付: 2026-06-28
- ステータス: 採用（Phase1・Phase2 実装済 / Phase3 未）

## 背景 / 何を決めるか
- 複数人で手動テストを回すため、**アカウント / ログイン / 権限・データ分離**を入れる（案B）。
- これは CLAUDE.md・design.md §8 で「**まだ作らない（核の検証後・ホスト化と同時）**」としていた領域。
  ユーザーの明示指示により**解禁**する。最大リスク（作り込みすぎて完成しない・§5.3）を避けるため**段階分け**する。

## 決定（アーキテクチャ）
1. **認証ライブラリ: Auth.js v5（`next-auth@beta`）**。Next.js 16 App Router 対応。
   - **Next.js 16 ではルート保護は `proxy.ts`**（旧 `middleware.ts` は使わない・最新docsで確認）。
   - ルートハンドラ `app/api/auth/[...nextauth]/route.ts`、設定は project root の `auth.ts`。
   - 必須env `AUTH_SECRET`（`.env` で受け取り**ハードコード禁止**・`.gitignore` 済み）。
2. **認証方式: メール＋パスワード（Credentials provider）を主**にする。
   - 理由: 承認を担う**ディレクター（業務）は GitHub アカウントを持たない可能性**があり、§6.7 の一級ユーザー。
     GitHub OAuth だけだと排除してしまう。**GitHub OAuth は後付けの追加プロバイダ**として将来検討。
   - パスワードハッシュは **Node 標準 `crypto.scrypt`**（依存追加なし。node:sqlite と同じ「重い/ネイティブ依存を避ける」方針）。
   - セッションは Auth.js の **JWT 戦略**（Credentials は JWT 必須・セッションテーブル不要）。
3. **DBは当面 `node:sqlite` のまま**（リポジトリ抽象 `LedgerRepository` の背後）。
   - マルチユーザーのデータ分離ロジックは**クエリ層**で行い、DB非依存にする。
   - **PostgreSQL 移行はホスティングと同時（Phase3）**＝ decisions/0002 の「将来差替」をここで順序づける。
4. **権限・データ分離モデル（メンバーシップ）**:
   - `users`（id/email/name/role/passwordHash/createdAt）。role: `admin` | `member`。
   - `project_members`（project_key / user_id / role: owner|member|viewer）。
   - 参照可否は**プロジェクト単位**：所属メンバーのみ閲覧、ロールで編集可否。課題/レコード/結果はプロジェクトに従属。
   - **記名（attribution）**: 結果・レコードに `created_by`（誰がテスト/承認したか）。
5. **初回ブートストラップ**: 最初に登録したユーザーを `admin` にする（以後 admin が管理）。

## 段階分け（各フェーズで動く・止めない）
- **Phase 1 — 認証の土台**: Auth.js + Credentials、`users` テーブル、ログイン/サインアップ、全ルート保護、
  現在ユーザー表示、結果への記名（created_by）。※データはまだ全員に見える（分離は Phase2）。
- **Phase 2 — メンバーシップ & 分離**: `project_members`、全クエリを所属プロジェクトに絞る、
  メンバー管理UI（メール招待）、ロールによる編集権限。
- **Phase 3 — ホスティング & Postgres**: リポジトリを Postgres 実装に差替、デプロイ（Vercel + Neon/Supabase 等）。
  別 decision で着手（ホスティング先・データ移行・証跡のクラウド保存=0006/§8 をまとめて順序づける）。

## 理由
- 認証方式をメール+パスワードにするのは、**承認者（ディレクター）を排除しない**ため（核＝オラクル承認の担い手）。
- DB を急いで Postgres にしないのは、分離ロジックはクエリ層で書けば DB 非依存で、先に**ローカルで多人数運用を検証**できるから。
- フェーズ分割は §5.3「作り込みすぎて完成しない」最大リスクの回避。各フェーズ単体で価値が出る形にする。

## 捨てた選択肢とその理由
- **GitHub OAuth を主認証に**: ディレクター（GitHub未所持）を排除。技術職向けには便利なので将来の追加プロバイダに留める。
- **bcrypt/argon2 ライブラリ**: ネイティブビルドや追加依存。`crypto.scrypt`（標準）で十分安全。
- **いきなり Postgres + ホスティング**: スコープ肥大。分離は SQLite でも検証可能。ホスト化は Phase3 で順序立てる。
- **行レベルのユーザー所有（record単位の所有者制御）**: 粒度過剰。**プロジェクト単位のメンバーシップ**で運用に足りる。

## Phase 2 確定事項（実装済・ユーザー承認）
- **既存データの所有**: 既存の全プロジェクト（明示 project_meta ＋ issue_meta ＋ records由来の派生キー）を、
  **最初の admin の owner** にバックフィル（`backfillProjectOwners`）。メンバーが1人でもいるプロジェクトは触らない（冪等・非破壊）。
- **参加は招待制**: 追加できるのは**登録済みユーザーのみ**（メールで指定）。未登録は本人にサインアップしてもらう。
  自己サインアップは可能だが、サインアップ自体ではどのプロジェクトにも所属しない（owner/admin が招待して初めて参加）。
- **権限**: `admin`(グローバル)=全プロジェクトにフルアクセス（システム運用者）。`owner`=メンバー管理可。
  `member`=試験作業可（観測/採用/結果/HTTP/証跡/優先度/承認）。`viewer`=閲覧のみ（編集系UIは非表示・サーバ側でも拒否）。
- **読み取り分離**: 一覧/ダッシュボード/サイドバー/Excel/項目詳細/証跡配信を、**所属プロジェクトに絞る**（admin は全件）。
- **書き込み保護**: 全 mutate 系 Server Action で `assertCanEdit*`（プロジェクトの有効ロールを確認）。
  メンバー管理は `owner/admin` のみ。**最後の owner は降格・削除できない**（管理者不在を防ぐ）。
- **プロジェクト作成**: 作成者を自動で `owner` に登録（以後そのプロジェクトは作成者の所有）。
- 実装: `app/lib/access.ts`（判定の単一窓口）/ `project_members` テーブル / `/project` にメンバー管理UI。

## 影響・前提（後で覆すとき確認すべきこと）
- `.env` に `AUTH_SECRET`（と将来 GitHub OAuth の client id/secret）。**コミットしない**。`.env.example` に雛形のみ。
- node:sqlite はプロセス内・単一ファイル。**多人数同時書き込みは小規模なら可**（書込は直列化）。本格運用は Phase3 の Postgres。
- 既存データは**ユーザー無し**で作られている。Phase1 は非破壊（全員可視）。Phase2 の分離導入時に
  「既存プロジェクトを最初の admin の所有にバックフィル」する（非破壊・冪等）。
- ルート保護で CLI（`src/cli`）は影響を受けない（CLI はローカルの台帳直アクセスのまま）。
