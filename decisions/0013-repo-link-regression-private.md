# 0013. プロジェクトのGitHubリポジトリ連携・デグレ観点・private対応

- 日付: 2026-06-28
- ステータス: 採用

## 背景 / 何を決めるか
- private リポジトリが UI から観測できない（トークン未解決）。
- 課題作成時のソースと PR の連携方法が分かりにくい。
- ソース（変更/PR）を観測するとき、デグレ（既存破壊）観点を補強したい。

## 決定
1. **private 対応**：UIサーバのGitHubトークン解決を「`.env` の GITHUB_TOKEN → 無ければローカルの `gh auth token`」に。
   PAT を手で作らなくても、ログイン済み `gh` を自動利用して private を読む（ホスト時は GITHUB_TOKEN を設定）。
2. **プロジェクト↔リポジトリ連携**：project に `repo`（owner/repo）を追加。作成/編集で設定（URL貼付も正規化）。
   - 課題作成時、連携リポジトリがあれば **PR番号だけ（例 `123`）/ パスだけ** で指定可（owner/repo を補完）。
3. **デグレ観点の補強**：観測フォームに「デグレ観点を強化」チェック（既定ON）。ONで Pass2 に
   後方互換・既存フローへの波及・以前通っていたケースの破壊などの観点（`lenses.md` の regression ブロック）を注入。

## 理由
- ローカル前提（§5.1）では `gh` 認証が既にあるのが普通。それを使えば private が即動く。
- リポジトリ連携で「PR番号だけ」で課題が立てられ、運用が軽くなる（PRレビュー起点＝§7）。
- ソースが「変更」のときの最大関心はデグレ。観点として明示注入すると質問が要点に寄る。

## 捨てた選択肢とその理由
- **private は GITHUB_TOKEN 必須のまま**: PAT 手作成は摩擦。gh フォールバックで解消。
- **PRを一覧から選ばせる**: GitHub API で open PR 取得は将来。まずは番号入力＋リポジトリ連携で十分。
- **デグレを常時ON固定**: 新規実装（変更でない）には過剰なことがある。チェックで切替（既定ON）。

## 影響・前提（後で覆すとき確認すべきこと）
- `gh auth token` をサーバから実行する（ローカル/自ホスト前提）。ホスト共有時は GITHUB_TOKEN を使い、shell実行はしない構成にする。
- リポジトリ連携は project 単位。課題のソースは引き続き課題が持つ（連携は入力補完に使うだけ）。
- デグレ観点は viewpoints への追記。観測対象が「変更」でない場合は OFF 推奨。
