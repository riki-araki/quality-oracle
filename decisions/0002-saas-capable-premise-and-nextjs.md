# 0002. ホスト型SaaSを将来の選択肢として前提に追加し、スタックを Next.js に決定

- 日付: 2026-06-28
- ステータス: 採用（0001 の「ローカル実行のみ」前提＝§5.1 を部分的に更新。0001 のその他の決定は引き続き有効）

## 背景 / 何を決めるか
管理画面などへの拡張を見据え、UI/アプリ層の技術スタックを選定する過程で
「拡張性を考えると Next.js では」という論点が出た。
検討の結果、これは**フレームワーク選択ではなく事業前提の問題**だと判明した。
Next.js の拡張性（App Router・APIルート・サーバー実行・認証/マルチテナント基盤）が
本当に効くのは「ホスト型・マルチユーザーのWeb製品」であり、
0001/§5.1 の「ローカル実行のみ」という前提とは噛み合わないため。

開発者本人が「将来は SaaS としてホスト提供も検討している」と明言した。
よって前提を更新し、到達経路のあるスタックを選ぶ。

## 決定
1. **将来のホスト型SaaS提供を、視野に入れる選択肢として前提に追加**する（＝今すぐ作るのではない）。
2. §5.1 を「**ローカル実行のみ**」から「**ローカル優先・ホスト対応可能（local-first, hosted-capable）**」へ更新。
   ローカルを既定（プライバシー・限界費用ゼロ）として維持しつつ、
   マルチユーザー/ホスト提供へ**作り直しなしで到達できる設計**にする。
3. アプリ/UI層のスタックを **Next.js（App Router・TypeScript）** に決定。
   ローカルAPIは Next の route handlers が担う（別途サーバーフレームワークを足さない）。
4. **engine（観測 Pass1 / 尋問 Pass2 / 承認 / §6.9 台帳）はフレームワーク非依存のモジュールに分離**する。
   CLI・ローカルUI・将来のホストが**同じ engine** を呼ぶ＝拡張性の継ぎ目はここに置く。
5. 保存は**リポジトリ抽象**の背後に置く。ローカル = SQLite（今）、ホスト = PostgreSQL（将来）。
6. マルチユーザー/認証/テナント分離は「**将来の対象（in-scope）**」へ格上げ。
   ただし**今は作らない**（スコープ規律 §5.3 は維持）。

## 理由
- SaaS が視野にある以上、ローカル特化スタックで始めて後でホスト用に包み直すより、
  最初から到達経路のある Next.js の方が総作り直しを避けられる。
- ただし「フレームワークの重さ」ではなく「engine の継ぎ目」が拡張性の本体なので、
  engine を分離しておけば UI 層（Next）が育っても核は安定する。
- ローカル既定を捨てないことで、0001 が積み上げたプライバシー・限界費用ゼロの強みも保持できる。

## 捨てた選択肢とその理由
- **Vite+React+Hono のままローカル特化**: SaaS を視野に入れた以上、将来ホストで包み直す手間が出る。却下。
- **ローカルのみを堅持（0001/§5.1 据え置き）**: SaaS の可能性を閉じる。本人の方針と不一致。却下。
- **今すぐ SaaS を作り始める**: §5.3（作り込みすぎて完成しない＝最大リスク）に逆行。
  「方向は Next、依存と機能は各スライス着手時のみ追加」に留める。

## 影響・前提（後で覆すとき確認すべきこと）
- **コストの罠は依然有効**: §5.1 の「クラウドでの実行は使われるほど赤字」は生きている。
  重い実行（LLM 呼び出し・将来のテスト実行）は**ホストの致命的コスト経路に載せない**。
  顧客の API キー／ローカルランナーで負担し、SaaS 側は UI・台帳・管理に寄せる**ハイブリッド**を既定線にする。
- **プライバシー**: ホスト時はコード/台帳が外部に出る。ローカルを既定に保ち、
  ホスト送信は**明示オプトイン**にする（知見ゼロ実装のコードは機微なため）。
- **スコープ規律**: Next 採用は「方向」。次の一歩（engine 切り出し＋§6.9 Zod スキーマ＋台帳）に Next は不要。
  Next/DB/認証の依存は、そのスライスに着手する時だけ足す。
- **0001 の他項目**（オラクル引き出しが核 / 買う人と使う人の分離 / E2E 優先 等）は変更しない。
