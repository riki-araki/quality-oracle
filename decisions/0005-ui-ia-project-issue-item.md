# 0005. 画面の情報設計を Project→課題→項目に、UIをモダンSaaS調へ

- 日付: 2026-06-28
- ステータス: 採用

## 背景 / 何を決めるか
核（オラクル引き出し）が実コードで価値を生むと検証できた（run=93d950 ほか）ため、その出力を
「見せる/管理する」層に投資する段階に入った（decisions/0002 で SaaS視野は前提）。
情報設計と見た目の方向を決める。

## 決定
1. **情報設計を3階層**にする：
   - **Project = リポジトリ**（または「ローカル」）
   - **課題 = PR / 指定範囲**（1レビュー単位）
   - **項目 = 台帳レコード**（質問・承認・生成テスト）
2. 当面は**専用テーブルを作らず、run の `codeRef.path` から Project/課題を導出**する（移行ゼロ。`app/lib/model.ts`）。
   明示的な Project/課題の作成導線（PR/範囲を指定して観測を流す）は次スライス。
3. UI は **Next.js + Tailwind CSS v4** でモダンSaaS調（ダーク・Linear風コンパクト・3ペイン）。
4. **✓スルー対策を内蔵**（最重要）：未レビュー＋`confidence=low`を上段固定、未レビュー件数を警告表示、
   **一括✓ボタンは置かない**。§6.7「✓で流すと掛け違いが温存される」を UI で抑止する。

## 理由
- Project→課題→項目は §7（PR＝エンジニアが受け取る瞬間）に一致し、複数人が同一フォーマットで管理できる。
- 検証で判明した最大の弱点が「✓スルー」。綺麗にするほど雑な全承認が速くなるため、見た目刷新と
  「ちゃんと吟味させる」を同時に設計する必要がある。
- codeRef からの導出なら移行ゼロで3階層を実現でき、スコープを小さく保てる（§5.3）。

## 捨てた選択肢とその理由
- **すぐ専用 Project/課題テーブル＋作成CRUD**: スコープ過大。まず読み取り＋承認の3階層と見た目で価値を出す。
- **手書きCSSのまま磨く**: モダンSaaS調を速く安定的に作るには Tailwind が適切。
- **証跡(画像/S3)・Backlog共有を同時に**: コモディティ層（§3.1）。引き続き後段（design.md §8）。

## 影響・前提（後で覆すとき確認すべきこと）
- 導出方式のため、課題の「作成」は観測を流すこと＝CLI 側に依存。UI からの観測実行・明示課題化は次スライス。
- ✓スルー対策はUIの工夫止まり。最終的には「未確認のまま✓した割合」(§6.10①運用版)を指標化して可視化したい。
- 旧 `/tests` 横断一覧は課題詳細に統合（項目内にテスト表示）。横断ビューが要れば別タブで復活可。
